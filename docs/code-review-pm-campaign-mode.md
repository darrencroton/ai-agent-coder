**Reviewer:** Claude Fable 5.1 (post-run owner review), 2026-10-23. **Inputs:** HANDOFF.md, the PM's run `notes.md`, the frozen plan `archive/implementation-plan-pm-campaign-mode.md`, the full diff and surrounding code, the test suite, and three delegated passes (mechanical validation on Sonnet 5.5; a documentation audit and an unanchored second read of the Python, both on Opus 5.5). ## Executive summary

The plan's goals are met. The branch delivers protected paths (policy loader, plan-time refusal, run-state freeze, `grant` refusal, floor fact 5), the file-based question channel for both loops, the four child commands on a private tmux server, the Developer-prompt and skill text, the VISION revision, the campaign reference and dossier template, a model-free README trial, and the CONTRIBUTING, CHANGELOG and root README updates. The code is careful, well commented, consistently fail-closed in its error paths, and tested at the boundaries the plan named: 638 PM tests pass (one known tmux-under-load flake, green in isolation), the other three suites pass, differential lint is clean with Python and Markdown covered, and the CI greps and doc links pass locally. The PM's run was well managed: review findings converged on every multi-round slice, and the PM's delegated decisions (PM-D1 to PM-D5) were sound and are endorsed below.

Two findings gate the verdict, and both are cheap to fix:

1. **The run token leaks into a fresh tmux server's global environment** (pre-existing in `sessions.start_session`; reproduced here on tmux 3.5a). Any run on a fresh `PM_TMUX_SOCKET`, including the README's own trial, exposes `PM_RUN_TOKEN` to `tmux show-environment -g` from inside the Developer session. `launch-child` patched this locally; the owning layer did not. One scoped `unset` in `start_session` closes it.
2. **A slash-less protected entry naming a directory fails open** (the PM's recorded plan defect PD-1). `check-plan` refuses a surface under `instruments`, but `grant` and fact 5 match the entry exactly, so a grant into the subtree and a change there both pass. The documentation carries a caveat; protection should not depend on a caveat. A protection-specific matcher of about ten lines closes it and lets the caveat go.

Below those: a default socket name that can exceed the Unix socket path limit (the occupancy guard then passes on a tmux error and the launch leaves a branch and worktree behind), `stop-child` trusting a child-writable manifest for the server it kills, and a cluster of documentation defects in `campaign-mode.md` that a Campaign Manager following it would hit on its first real node: the cleanup capture that loses a partially staged file, child output that `git worktree remove` deletes before any receipt can be re-verified, no rule that a node policy must carry the product policy's entries, no external-side-effect prohibition on the one PM seat that merges, and a child HANDOFF.md that fails floor fact 7 in a linked worktree because the launcher's exclude path does not exist there.

**Verdict: FAIL on the two P1 findings, otherwise PASS WITH RISKS.** Recommendation: one follow-up slice for the two P1 fixes and the socket-name bound, one for the documentation corrections, then merge to `main`. Everything else is a residual to schedule, not a blocker.

## Findings

Severity follows the `code-review` skill: P0/P1 only where the path to the defect is stated.

### P1

**1. `sessions.start_session` copies an exported `PM_RUN_TOKEN` into a new tmux server's global environment.** `skills/project-manager/scripts/pm_lib/sessions.py:203-220`. The session shell runs `unset PM_RUN_TOKEN`, but tmux seeds a *new server's* global environment from the process that starts it. Reproduced on this machine: `PM_RUN_TOKEN=x tmux -L probe new-session -d "unset PM_RUN_TOKEN; sleep 20"` then `tmux -L probe show-environment -g PM_RUN_TOKEN` prints the token, while the session-scoped query reports it unset. Reachability: any `start-slice` where the PM shell has exported the token (the documented way to hold it) and the socket's server does not yet exist: a fresh `PM_TMUX_SOCKET`, which the README trial and every per-process test socket use, or a default server that has exited. A Developer then reads it with `tmux show-environment -g`, and the token authorizes every state write for the run. This is pre-existing and outside the plan's contract, which is why the PM left it as a follow-up; it is reported here because the change interacts with it: `launch_child` (`campaign.py:354`) added a scoped unset around its own `start_session` call, which is the right idea in the wrong layer. Fix: move that scoped unset into `start_session` itself, around the `new-session` call, and add a test that starts a server on a fresh socket with the token exported and asserts `show-environment -g` does not carry it (the campaign test at `test_campaign.py:494-499` is the model). Then delete the duplicate in `campaign.py`. Belt and braces: `tmux set-environment -g -u PM_RUN_TOKEN` right after the server starts.

**2. A plain protected entry that names a directory protects nothing below it at `grant` or fact 5, while `check-plan` behaves as if it did** (the PM's PD-1). `plan.py:386-455` (`load_policy`), `plan.py:362-379` (`protected_overlap`), `slice_ops.py:652` (`grant`), `floor.py:211` (`_fact_surface`), all through `git_ops.is_authorized_path` (`git_ops.py:170-186`), which matches a plain entry by equality. Probe: `is_authorized_path("instruments/check.py", ["instruments"])` is `False`; `protected_overlap("instruments/check.py", ["instruments"])` is `"instruments"`. So `check-plan --policy` and `init --policy` refuse a plan surface under the directory (segment-wise prefix compare), but `grant --path instruments/check.py` is accepted and a committed change there passes fact 5. Reachability: a policy author writes `"instruments"` instead of `"instruments/"` (legal entry syntax, and the natural spelling), and a PM grants into the subtree on a Developer's request. The PM mitigated it with a sentence in `run-state.md` and `campaign-mode.md`; the repository's own convention is fail closed by default, and the two enforcement points now disagree about what one entry means. Fix (recommended): a protection-specific matcher, `git_ops.is_protected_path(path, protected)`, that is `is_authorized_path(...) or any(path.startswith(e + "/") for plain e)`, used by `grant` and `_fact_surface`; this never widens an *authorized* surface, keeps plan-time and runtime in agreement, and covers directories created later. Add one grant test and one floor test with a plain directory entry, and remove the two caveat sentences. Alternative: `load_policy` refuses a plain entry that is an existing directory when `repo` is given; weaker, because a directory the campaign creates later escapes it.

### P2

**3. The default socket name can exceed the Unix socket path limit, and the occupancy guard passes when tmux errors.** `campaign.py:79-88` (`child_names`), `campaign.py:305-311`, `sessions.py:301-315`. tmux's socket lives under `/private/tmp/tmux-<uid>/<name>`; `sun_path` is 104 bytes on macOS, so a socket name of roughly 80 characters fails with `File name too long` (reproduced by the independent reviewer with an 84-character name). The default is `pm-child-<branch>-<hex>` and the campaign branch convention is `campaign/<id>/<node>`, so a descriptive id plus node name reaches the limit. When it does, `sessions_with_prefix("")` returns `[]` on the `list-sessions` error, the precondition passes, the branch and worktree are created, and `start_session` fails, leaving both behind for hand removal. The same guard passes when tmux is absent, which is only detected inside `start_session` after the worktree exists (the PM listed this as a follow-up). Fix: bound the branch component in `child_names` (truncate to, say, 40 characters, keeping the random suffix); add `shutil.which("tmux")` to the preconditions; make the occupancy check distinguish "no server running" from any other `list-sessions` failure and refuse on the latter.

**4. `stop-child` kills whatever server the manifest names, and the manifest is child-writable; `--socket default` is the operator's server.** `campaign.py:130-144` (`load_manifest`), `campaign.py:553-585`, `campaign.py:91-103`. `child.json` sits in `<worktree>/.pm/campaign/`, inside the child's working tree. `check_socket_name` refuses only blank, whitespace and `/`, so a manifest socket of `default` passes, and `tmux -L default` is the unscoped default server (confirmed: both list the operator's session here). `read_child_runs` deliberately treats the child's `run.json` as unverified; `child.json` is trusted in full. The plan's threat model excludes a determined fabricator, so this is rated P2, but the cheap hardenings are worth taking: refuse the literal `default` in `check_socket_name` (at launch and at manifest load); have `stop-child` confirm the server hosts the manifest's `campaign-*` session, or at least one `campaign-*` session, before `kill-server`, and otherwise print and refuse; and let the CM pass `--socket`/`--session` from its own `work.md` record as a cross-check. The session check also closes the Slice 4 residual the PM recorded (a re-run of `stop-child` against child A's manifest killing child B on a reused socket).

**5. The cleanup capture rule overwrites a partially staged file before capturing it.** `references/campaign-mode.md:79`, `references/dossier-template.md:100`. The text runs `git add -A` and then writes `git diff --cached --binary HEAD` as "staged, unstaged and new non-ignored files". When HEAD, index and working tree all differ (`MM` in `status.txt`), `add -A` replaces the staged version, the patch holds only HEAD to working tree, and `--force` then deletes the worktree; a nested repository (`?? dir/`) is recorded as a gitlink with none of its content. The PM recorded this as a tolerated residual with the right fix. Fix: write `git diff --cached --binary` to `validation/<node>/staged.patch` before `add -A`, drop "staging is harmless", add `staged.patch` to the template's `validation/` layout, and keep the worktree when `status.txt` shows a nested repository.

**6. Git-ignored child output is deleted by `git worktree remove` and is never archived, yet receipts hash it.** `campaign-mode.md:82` sends child output to git-ignored directories; the copy list at `:79` covers HANDOFF.md, `.pm/campaign/`, `.pm/runs/<id>/` and the state root; `:114` has a receipt record "artifact hashes". `git worktree remove` deletes ignored files without `--force`. An evidence node's artifacts therefore cannot be re-hashed after cleanup. Fix: either copy the artifacts a receipt hashes into `validation/<node>/` before removal, or state that the hash is the only record and the artifact is not retained.

**7. Nothing requires a node policy to carry the product policy's entries.** `campaign-mode.md:105`: "Every policy handed to a child lists the product repository's committed policy file path explicitly" requires only that one path. A node policy of `{"protected_paths": ["campaign-policy.json"]}` complies and protects no instrument; `init` reads one `--policy` file and the toolkit never reads the product policy. Fix: "each node policy holds every entry of the product's committed policy file plus that file's own path, minus only the instrument an instrument-class node builds", and have reconcile check the product policy against the SHA the brief pins for it (`dossier-template.md:38`).

**8. The Campaign Manager has no push, deploy or external-side-effect prohibition.** `campaign-mode.md:16` (Seats, CM "Never"), `:163` (launcher), `SKILL.md:20`. SKILL.md now says "the charter above binds every PM in plan mode unchanged", so the Charter's "push, deploy, or cause external side effects" no longer reaches the one PM seat that performs merges. Fix: add "pushes, deploys or causes external side effects" to the CM row and the launcher's never-line, and say in SKILL.md that the charter's prohibitions bind the CM too, the planning prohibition excepted.

**9. Enforcement overclaims.** `skills/project-manager/README.md:13`: "entries no plan surface, `grant` or commit can reach". A commit can reach a protected path; fact 5 refuses acceptance of the slice, and only for Git-visible files, only within a child's floor, and not for inherited commits from a stopped head or for CM merges (`campaign-mode.md:76` says so itself). `campaign-mode.md:110`: "no later node can change the instrument a target is measured by" holds only if every node policy lists it (finding 7). CONTRIBUTING requires every guarantee to name its layer. Fix: "refused at plan time and at `grant`; fact 5 refuses acceptance of a slice that changes one (mechanical, Git-visible files only)", and name the CM's policy discipline as judgement.

**10. The Developer Stop rule reads as "stop while waiting"** (the PM's PD-2). `references/developer-prompt.md:66`: "Stop (status "blocked") when: a second reading is also implementable and PM has not answered your question about it". For the whole of a Developer's wait PM has not answered, so a literal reading asks and then blocks; once `blocked` is written `pm answer` is refused because `result.json` exists. Workflow step 3 and the closing "a question, not a stop" sentence carry the intent, and the Codex reviewer caught it in-run. Fix: "and PM's answer did not settle it (an unanswered question is not a stop: wait for the pointer)". Related: step 3 offers "a tolerance" as a question while the unconditional "the contract leaves a rule or boundary unstated" is a stop; exclude a tolerance PM can give in a line from the stop clause.

**11. A child PM's HANDOFF.md fails floor fact 7 in a linked worktree unless the owner pre-excludes it.** `skills/implementation-plan/SKILL.md:256` (unchanged Mode B text) read with the new campaign-child block at `:244`. The launcher says "git-ignored (add it to .git/info/exclude if it is not)". In a `launch-child` worktree `.git` is a file; git reads the main repository's `info/exclude`. Verified: an unexcluded HANDOFF.md in a linked worktree shows as `?? HANDOFF.md`, which `meaningful_status_lines` reports and fact 7 fails at every `finalize`. Fix: one clause in the campaign-child block (`$(git rev-parse --git-path info/exclude)`), and a sentence in `campaign-mode.md` telling the CM to exclude HANDOFF.md in the product repository before the first launch.

**12. Test gaps on new failure paths.** `tests/test_campaign.py:357-370`: the manifest case `{"socket": "a/b"}` fails the missing-fields check before `check_socket_name` runs, so the manifest socket guard is asserted for the wrong reason. Untested: `git worktree add` failure and its leftover report (`campaign.py:316-324`); a `send_prompt` failure after the manifest is written (only the readiness failure is covered); `wait_child`'s `pane_live_error` and `stop_child`'s `pane_error`; `deliver_answer`'s question-rename failure branch (`slice_ops.py:1252-1256`); and the plain-directory protected entry (finding 2). ### P3

- **Question text is uncapped by width and undelimited.** `campaign.py:417-422`, `slice_ops.py:1135-1142`, `cli.py:621-627`. Forty lines of arbitrary width can flood the PM's context, and the text is printed raw after `question present: yes`, so a Developer can write lines that mimic `observe`'s own report lines. Cap by bytes with a truncation marker and fence the text.
- **`TypedNotSubmitted` leaves no `answer` event.** `slice_ops.py:1297`. The docstring calls the event the durable record; on a typed-but-unsubmitted pointer the answer exists only in the Developer-writable file. Append an `answer` event marked undelivered before re-raising.
- **`deliver_answer` rollback.** `slice_ops.py:1252-1262`. A failed restore rename is swallowed, and the next `answer` then fails with the misleading "numbering disagree" message; the restore rename would overwrite a fresh `question.md` written in the window (`_restore_rotated_attempt` uses `os.link` to avoid exactly this). Append the cleanup failure to the raised error and use the link-then-unlink pattern.
- **Self-protection appends an unvalidated path.** `plan.py:448-454`. A policy file named with `[`, `*` or `?` is read as a glob by the matcher (`policy[1].json` is not protected; a root-level `[x].json` has an empty literal prefix and refuses every plan). The PM recorded this; refuse such a name at load.
- **`check-plan --repo` is not resolved to the toplevel and `--policy` without `--repo` skips self-protection**, so `check-plan` can pass a plan that `init` refuses (`cli.py:344` vs `:369`). - **`stop-child` always prints "killed tmux server"** because `kill_server` ignores every non-zero exit (`campaign.py:585`, `sessions.py:333`). Re-probe `list-sessions` after the kill, or return a bool.

- **Dirty-tree renames still show only the destination** (`git_ops.py:69-80`); fact 7 still fails, so no bypass. The plan excluded it; `git status --no-renames` would make the evidence complete.
- **Documentation:** `campaign-mode.md:17` "depth is fixed at two" is prompt-level only (`launch-child` needs no token); `:23` "loses nothing a restart needs" holds only if `work.md` is kept current; `:134-135` the scratch test says an owner-approved node builds the instrument but the node sequence has no such node, and says N2's "report" is copied where the loop and template say "receipt"; `dossier-template.md:3` says it restates no rules and then restates the capture commands and the "only list of protected paths" rule (the drift this creates showed when `cdd4eb8` had to edit both files); the PM README privacy table does not cover the dossier's `validation/<node>/` copies of the child pane, which carries the child's `PM_RUN_TOKEN=` line (low exposure: that run's state root is deleted with the worktree); SKILL.md's *Reading a defective plan* lost the "stop with the defect written up" guidance (authorized by Slice 6; one clause would restore it).
- **VISION's remaining text** still describes the top rung as one plan under a PM (`docs/VISION.md:15`, `:25-33`) and ends the autopilot bullet with "keeping planning human-approved is a feature" right after allowing CM-written plans (`:93`). The plan scoped the revision to two paragraphs; this is a deliberate follow-up revision for the owner, not drift.
- **Test flake.** Two modules (`test_ledger`, `test_finalize`, and once `test_sessions`) lose their per-process tmux server under full-suite load; each passes in isolation. Harden `pm_test_helpers` so the per-process server is started with a long-lived placeholder session, so a fake harness that exits at once cannot take the server with it.
- **Housekeeping:** the plan file is archived as `archive/implementation-plan-pm-campaign-mode.md` after the run (the tracked deletion needs a commit); 18 commits are unpushed; two codex app-server daemons from the Slice 4 incident family are still running (pids 8797 and 22477 at review time); `test_campaign` leaves dead default-socket files under the tmux socket directory.
