# Changelog

Notable changes to this repository. Format follows [Keep a Changelog](https://keepachangelog.com/); versions follow [SemVer](https://semver.org/) once tagged. Releases are tagged from `main`; v1.0.0 will mark the first stable contract for the skills, the Project Manager CLI, and the plan format.

## [Unreleased]

### Added

- **`code-health` skill: deterministic structural evidence above lint.** Adds differential and absolute repository analysis for composition, file-size distributions, exact whitespace-normalized repeated blocks, Python AST cyclomatic complexity, internal dependency structure, optional Lizard multi-language complexity, and optional Git revision/churn context. Dependencies follow lint's safety contract: analysis never installs, detection names missing coverage, and installation is a separate dry-run command unless a human explicitly supplies `--yes`. The analyzer emits a language-by-metric coverage matrix and bounded investigation candidates, never an aggregate quality score or unhealthy verdict; successful evidence collection exits zero regardless of what it finds. Facts remain separate from model judgment, unavailable measurement never reads as clean, and ratios or ranks are anomaly prompts rather than universal targets.

- **PM can tell a reviewer what it has already ruled on — `review --adjudicated TEXT` (repeatable).** Measured need: across one three-slice run the commissioned `code-review` produced four findings and *zero* were actionable — three were one recurring class (unlisted-input coercion holes leaking `TypeError` ahead of a `float()` coercion) that PM had already adjudicated as forbidden by the plan's own binding "validate exactly the listed rejection conditions … do not add further input validation" clause. The reviewer re-derived it each slice because `notes.md` is Developer-directed and reviewers never see it. Adjudications now render into the reviewer prompt as a bulleted block above the frozen contract and deliberately *separate* from it, since a PM ruling is not a plan clause. Handing over `notes.md` wholesale was rejected as the fix: in that run it was 7KB of Developer-directed instruction, much of it actively misleading to a reviewer. Three guardrails stop this becoming a suppression channel: the template states an adjudication bounds attention only and can never widen the authorized surface or weaken a criterion; an adjudication is settled *only for as long as the reviewer agrees with it*, and one it judges materially wrong gets a **full finding** with normal severity, reachability, and evidence, labelled as dissent — an earlier draft capped dissent at one line, which a high-effort review correctly flagged as suppressing the analysis precisely where PM most needs it to overturn a bad ruling; and the prompt is now persisted (below). PM-authored text is substituted, never re-formatted, so a brace inside an adjudication is inert rather than a template error, and newlines within an item are collapsed so a multi-line ruling cannot imitate a later prompt section.
- **Every commissioned reviewer's rendered prompt is persisted as `review-<n>-<skill>-<tool>-prompt.md`.** Previously the reviewer prompt was passed inline as an argv string and written nowhere — harmless while it was wholly derived from the plan, but once PM can inject free text narrowing what a reviewer reports, a report's *omissions* become unauditable: the human could not see what the reviewer was told to skip. Written before the reviewer runs, so a timeout, crash, or non-zero exit still leaves the commission auditable rather than only its silence. That guarantee needed a second fix to actually hold: artifact sequence numbers were derived from *recorded* reviews, and a failed commission records none, so a retry reused the failed attempt's number and overwrote exactly the evidence this was added to keep. Numbering now takes the max of recorded reviews and any `review-<n>-*` file already on disk, so a failed attempt's artifacts survive its retry. Mirrored into `.pm/` like the report and derived from the report's own path so the two cannot diverge, and added to the README's privacy table, since prompt copies embed the slice contract and the review skill's full bundle.
- **`run-report.md` reports total run time, and `status` prints the run's `recorded event span`.** Derived once in `state.run_elapsed()` from the event log the toolkit already timestamps, so answering "how long did this take" never means hand-parsing `events.jsonl` — which is exactly what the one observed run had to do, because the launcher asked its PM to report run time while the run record carried no timing at all. Machinery over memory: the number is in the record PM reads at the end, not an instruction it must remember. The endpoints ship beside the duration so the figure is self-auditing — a reader asked to double-check it can verify the span without reopening the log. Spans min-to-max rather than first-to-last line, so an out-of-order append cannot yield a negative or truncated figure; malformed and missing timestamps are skipped; and a log with no parseable timestamp renders `unknown` rather than a fabricated `0s`.

- **`lint` skill: deterministic hygiene before model-based review.** A new skill and `scripts/lint.py` runner that reports only the findings a change *introduces* — it lints the changed files at head, lints the same files at a base ref in a throwaway detached worktree, and reports the signature-level difference, so pre-existing debt cannot block a change and a newly added unused import cannot pass. Motivated by measurement: across five supervised runs of one plan, 11 of ~14 non-correctness findings were mechanical (dead locals, a malformed Markdown table whose extra cell renders as silently dropped, warnings on supported code paths), and both commissioned LLM reviewers missed every one while correctly finding subtle semantic defects. Table-driven tool registry covering Python (`ruff check`, `ruff format`), Markdown (`markdownlint-cli2`, including MD056 table-column-count), C/C++ (`clang-format`, `cppcheck`, opt-in `clang-tidy`), Fortran (opt-in `gfortran -fsyntax-only`), any-language typos (`codespell`), plus a built-in `git diff --check`. Load-bearing invariants: `check` never installs anything (installing is a separate explicit human command, dry-run unless `--yes`, so an unattended Developer cannot use lint to route around its no-dependency-changes rule); a missing linter is reported as `unavailable` coverage rather than a pass, with `--require-coverage` turning that into exit 3; a linter that fails at the base ref is an error, not a pass, since it would make every pre-existing finding look new; and the tool set carries no complexity or naming metric, because a project's own conventions win over a generic rule. Deliberately **not** a ninth floor fact: the floor's eight facts are repository-integrity properties that are never legitimately violated, whereas lint is a quality signal this system places in recorded judgement above the floor — mandatory to run and recorded in the assessment, but a PM may accept over a finding with a reasoned tolerance, and a linter release adding one rule must not be able to hard-block an unrelated run. Wired into both modes: `scoped-implementation` step 4 and `commit` before staging (Mode A); the Developer prompt's validation step, PM's own independent rerun during assessment, and PM judgement guidance to lint before commissioning any review (Mode B). `code-review` now explicitly defers mechanical hygiene to `lint` instead of spending reviewer attention on it, and `implementation-plan`'s Validation Plan template asks for it. 38 unittest cases requiring no linter binary — every parser is tested against output captured from the real tool.

### Changed

- **Orchestrator monitoring now prefers timeout-bounded waiting over polling.** The workflow directs Developers to use one managed `wait` sized to the host's foreground-command limit, then limits `activity` checks to normal progress-update cadence or suspected trouble. Short `wait`/`activity` loops add no evidence and waste model turns.

- **Every Developer seat launches at its harness's fullest autonomy, and PM now assumes an operator sandbox around the whole run.** A supervised Developer has nobody to answer a permission prompt, so a prompt is not a safety feature — it is a silent stall, and the qwen run that motivated the earlier `--yolo` fix showed the failure is invisible to `finalize` until a human reads the pane. The Developer profiles now launch codex with `--dangerously-bypass-approvals-and-sandbox` (was `-s workspace-write -a never`), claude with `--permission-mode bypassPermissions` (was `auto`), and copilot with `--allow-all` (was `--allow-all-tools`, which left paths and URLs gated); opencode's `--auto` and qwen's `--yolo` were already maximal. Dropping codex's sandbox also deletes the `--add-dir <git-dir>` hack that existed only to let a sandboxed codex reach a linked worktree's git directory to commit, and with it the `reviewer_network`/`git_access_dir` parameters and the two profile flags behind them — `compose_command` now has one harness-specific branch (claude's `--session-id`) instead of three. The honest trade, stated in the README: codex's `workspace-write` seatbelt was the one *mechanical* boundary among the five, and the floor cannot replace it — it sees Git-visible worktree state only. Containment is now the process and filesystem isolation the operator runs PM inside — a container or VM, since a separate checkout stops nothing. Verified against the installed CLIs: codex 0.146.0 reports `permissions: YOLO mode` and claude 2.1.220 `bypass permissions on`, neither matching a hard-stop marker, and claude's bypass mode needs no acceptance dialog or user-global config change. Folder trust is untouched and still stops the run for a human — Copilot asks on a folder it has not been told to remember, regardless of `--allow-all`.
- **Headless qwen reviewers and delegates no longer hang on their first tool call.** `review.py` and the orchestrator's delegate profile both composed `qwen --prompt … --sandbox` with no approval flag, so qwen's classifier-gated Auto mode blocked on a confirmation a one-shot run cannot answer — reproducing as a hang until `--timeout`, and recorded in `references/qwen.md` as a caller-configuration problem "not a flag this launcher can pass". That was wrong: `--yolo` exists and the Developer seat has used it since the stall it was added for. Both paths now pass it, in both delegate access modes; the reference is corrected. It removes a mechanical approval barrier without widening authorization — the qwen profile was never mechanically differentiated between access modes and the delegate contract forbids exactly what it forbade before. One caveat, found by review and now documented rather than papered over: qwen silently reverts any non-default approval mode in a folder it does not trust, printing `Approval mode overridden to "default"` to stderr, so the fix holds only for a repository a human has trusted once. Relatedly, qwen's own trust dialog ("Do you trust this folder?", defaulting to *Trust folder*) matched none of PM's trust markers, meaning an interactive qwen launch could have had that dialog confirmed by the launch injection's Enter — the marker and a verbatim regression fixture are added. The codex, claude, and opencode reviewers keep their read-only modes — a reviewer produces a report rather than edits, so autonomy buys it nothing while read-only costs it nothing. Copilot reviewers move to `--allow-all` for the same reason as the Developer seat: a denied path or URL read silently degrades a review rather than stopping it.
- **The test suite is 29% faster serially, parallel-safe, and no longer touches the operator's tmux server.** Measured before: 467 tests in ~365 s, at 14% CPU — overwhelmingly sleeping, with 77% of all test time inside 57 tests. The single slowest test spent 60 of its 69 seconds on nothing: its fake harness changed the pane every 0.3 s from launch, and readiness for a non-codex/opencode harness is inferred from the pane *holding still*, so `wait_until_ready` burned its full 60 s deadline and gave up — non-fatally, so the test stayed green while wasting a fifth of the whole run. Fixtures whose event must land at a chosen moment are now gated on a trigger file the test touches, rather than on a delay timed from launch, which both raced the launch (a 7 s delay against a ~5 s launch) and had to be padded until it was slow as well as racy. `test_plan.py`'s 48 pure parser tests moved off the git-repo fixture they never used (9.03 s → 0.19 s; a `PlanTestCase` base now provides a plain temp directory). Duplicated fake-harness builders and lifecycle helpers — several drifted into slightly different versions of themselves — are shared from `pm_test_helpers`. Net: project-manager 351.6 s → 251.3 s over 320 tests, with two tests deleted (one an exact duplicate assertion, one a shape check that could not fail) and five merged onto launches their siblings already paid for. Every test process now pins its own tmux server via `PM_TMUX_SOCKET` (`tmux -L`), so the suite can no longer sweep, mutate the global environment of, or kill the operator's real tmux sessions — a hazard confirmed the hard way during this work, when a `TMUX_TMPDIR`-based attempt silently fell back to the default server because `$TMUX` was set. With that isolation and the run-id fix above, the ten project-manager modules run in parallel in ~100 s, verified over three consecutive clean sweeps.
- **Second calibration pass, from five supervised runs of one plan — three prompt clauses and one report field, deliberately no new machinery.** The evidence review of those runs proposed five toolkit changes; two were declined after reading the run artifacts rather than adopted. *Declined:* a reviewer reachability rule, because `code-review` already gates `P0`/`P1` on a stated reachability path and the artifacts show it being applied — every `P1` in the final run names a concrete producer path — with the residual reviewer disagreement tracing to an ambiguous plan rather than to reviewer calibration; and a `manifest.json` reconciling declared against observed run configuration, because `run.json` already records harness, model, effort, plan digest, reviewer, and attempt budget under HMAC, its `effort` *is* the flag the launcher composed, and the one observed mismatch was in an operator's separate notes rather than in the tooling. *Adopted, in `project-manager/SKILL.md` alone:* PM reads the output a slice produces for a human — a results table, a figure, CLI text — not just its exit code, since a command exiting 0 while printing ambiguous rows passed every other check in one run; PM closes each carried note out at the slice that inherits it, as closed with evidence or explicitly re-carried; and repeated adjudication of one plan section is re-framed by *cost* — rejecting a finding class repeatedly on cited evidence is free and is the system working, whereas one plan section that keeps costing attempts, or two commissioned reviews reaching opposite conclusions about it, is evidence of a defective plan and a better stop reason than "developer failed". A proposed hard counter ("stop past ~3 rulings on one section") was rejected: the most autonomous run of the five overruled the same finding class roughly ten times on measured evidence and would have been stopped by it.
- **`run-report.md` header records the reviewer and the attempt budget**, alongside the harness it already named. Those three are what decide whether two runs are comparable, and the header previously left two of them to notes kept outside the run.
- **`codespell` gains a `uv` install recipe, and a missing linter now says what would install it.** `uv` was already probed first, so `ruff` resolved to `uv tool install` while the other Python linter fell through to `pip install --user` on the same machine — one language, two mechanisms. Both now take the single path wherever `uv` exists, with the `pipx`/`brew`/`pip` fallbacks untouched for machines without it. `uv` is deliberately not promoted to universal installer: it cannot install `markdownlint-cli2`, `clang-format`, `cppcheck`, or `gfortran`, and the per-binary recipe table already handles that. `check` and `detect` share one hint that names the missing binaries, states plainly that **those checks did not run** — not that the language went unchecked, since another installed tool may cover it and `coverage` owns that answer — prints the `install` command, and points at `uv` only when a missing binary actually has a `uv` recipe. Previously `check` reported an unavailable language without saying what would fix it. `check` still never installs: SKILL.md now says outright that an agent finding a tool missing reports it and lets the human decide, in any mode.
- **`lint` ships a defect-focused default `ruff` config, because ruff's own defaults are taste.** Found on first real use, once the binaries were actually installed: with ruff 0.16 defaults the skill reported 26 findings on one calibration repo and 43 on the other, of which the great majority were style-with-judgement — import ordering, semicolons, imports below a deliberate `sys.path` fixup, and `C408`, which rewrites `config = dict(...)` to a literal and so fired on the *documented convention of the project it was linting*. That is exactly what SKILL.md invariant 4 forbids and what a linter must never do: outrank the plan. `config/ruff.toml` selects `F`, `E9`, `B`, `T10`, `DTZ`, `ASYNC` and pylint's error tier only, and records inline why each excluded family is excluded. The same two repositories now report 7 and 10 findings, every one a defect: unused imports and locals, `zip()` without `strict=` (silent truncation, a real numerical-code trap), `datetime.utcnow()`, and a re-raise losing its traceback. Applied exactly like the existing markdownlint default — only when the project has no `ruff.toml`, `.ruff.toml`, or `[tool.ruff]` table, since a bare `pyproject.toml` must not count as configuration or the default would be disabled almost everywhere.
- **`detect` on an unchanged tree says so.** It scopes to changed files by default, so a clean worktree printed "0 file(s) in scope" followed by "all selected tools installed" — literally true, but it reads as a green light when nothing was inspected. It now names the scoping rule and points at `--base`/explicit paths.
- **Calibration fixes from two Mode B runs (recorded in `PM_SKILL_IMPROVEMENTS.md`, since archived).** Both runs shipped no bad code but also failed to ship good code, exhausting their attempt budgets on correct-but-unreachable numerical findings. `code-review` now gates `P0`/`P1` on a stated reachability path (documented public surface counts by its documented domain; unreachable findings cap at `P2` and say what reaching them would take) and accepts an authorization check performed by the commissioning context. `project-manager` states that a passing floor means file-surface compliant and mechanically well-formed rather than correct, that a review verdict is a reviewer's opinion PM may accept over with a recorded tolerance, and that corrections belong batched into one steer; `status` and `finalize` now print attempts against the ceiling, and the README says when to raise `--max-attempts`. Every commissioned review now states authorization outright — PM checks the changed surface itself, plus the re-mirrored path of any drift-audit report recorded fresh against the same commit (never handed to a drift audit itself, which must stay independent) — replacing the "not supplied" caveat that opened every observed report. `implementation-plan` asks for `Acceptance Criteria` as an enumerable checklist of verifiable assertions, with declared input domains for numerical slices bounded by in-domain exceptions and what the CLI actually accepts, and treats a slice bundling new functions plus wiring plus docs as a split signal.
- **Breaking — Mode B replaced greenfield by "Mode B Lite."** The `project-manager` skill and its toolkit were rebuilt from scratch against an approved design package, and `docs/VISION.md` was replaced with the resulting timeless vision. The previous machinery is deleted, not migrated: the failure-signature taxonomy and repair-round classifiers, the circuit breaker and signature streaks, the dual state copy and `reconcile`, schema v4/v5 slice-entry validation of Developer-reported fields, `prior-slice-context.md` generation, reviewer-policy snapshots and `PASS`-verdict gating, the residual-finding and continuation-note ledgers, per-round artifact families, and the launch-contract reviewer forensics. Runs on any earlier PM state must be reinitialized.
- **Mode B Lite shape and validation.** One authoritative, HMAC-authenticated run state (`schema: lite-1`) under the worktree's git directory with a `.pm/` human-facing mirror; an eight-fact mechanical, non-waivable floor (plan digest, repo/branch identity, approval eligibility, result presence and slice identity, changed-files ⊆ authorized surface, commit ancestry/branch-head, clean worktree, hard-stop scan); a PM agent that assesses every slice from repository evidence and records the decision with reasoning; two risk levels (`standard`, `elevated`) derived mechanically from the plan and raisable only upward by PM; PM-commissioned independent `drift-audit` + `code-review` on elevated slices, pinned to the final commit and invalidated by any later tree change; a minimal Developer `result.json`; a bounded per-slice attempt budget; and a ten-command CLI. Stage 7 is complete: Runs A, B, and C all satisfied their acceptance bars, including 5/5 strong-pairing parity with zero interventions in Run B; the owner-confirmed anti-resurrection review also passed, closing the full implementation plan.
- **Equal first-class harness access.** Native Qwen Code joins Codex, Claude, Copilot, and OpenCode as a supported Developer profile (`--harness qwen`) as well as a Reviewer tool; model selection uses `-m`, and unsupported effort overrides fail closed. Harness profiles expose factual CLI differences but do not rank or restrict which tool the operator selects for a plan.
- **Hard-stop coverage and trust handling.** Qwen's observed `requires manual approval` phrasing is now recognized by the mechanical hard-stop scan. Directory-trust and permission dialogs remain human gates: PM documentation explicitly forbids acknowledging them through tmux or changing user-global harness configuration.
- **Breaking — `orchestrator` skill (formerly `ai-orchestrator`).** The executing agent is the Developer; a delegate is an external harness session launched in one of two access modes — `read-only` (evidence, drift-audit, code-review) or `read-write` (a bounded implementer inside an explicit `authorized_surface`/`non_goals`). This replaces the earlier Senior/Junior worker roles and the single read-only Reviewer role. Delegate requests use schema v3; scripts are `delegate_contract.py`, `delegate_sessions.py`, `delegate_jobs.py`; runtime state lives under `.orchestrator/`. All supported harnesses are equally eligible for either role, with harness-specific enforcement reported as fact rather than ranking.
- **Orchestrator session continuity and tracking parity.** Every Claude, Codex, Copilot, OpenCode, and Qwen launch now persists a launch-owned session ID when the harness exposes one, reports source-labelled activity with captured output as the universal fallback, and supports policy-revalidated continuation through a fresh `parent_label`/`-rN` request. Continuations require a terminal same-run, same-harness parent with an explicit captured ID, record auditable lineage, and fail closed without any global “resume last” fallback.

### Fixed

- **Two PM runs started in the same second can no longer share a tmux session — and reaping one run can no longer kill another's.** A run id was a bare one-second-resolution UTC timestamp, collision-checked only against run directories under a single state root — while every linked worktree deliberately gets its own root. Two runs launched in the same second in two worktrees or repositories therefore could not see each other, minted the same id, and produced the same `pm-<run-id>-s<NN>a<N>` session name on a tmux server that is global to the machine, so one run could observe, steer, or kill the other's Developer session. Reproduced directly: two unrelated temp repositories both yielded `pm-20260730T122423Z-s01a0`. Run ids now carry a random nonce (`<timestamp>-<6 hex>`); a PID was rejected as the fix because PIDs are reused and a tmux session outlives the controller process that created it. A second, independent defect on the same path: a run's sessions were swept by the string prefix `pm-<run-id>`, which also matches `pm-<run-id>-2-…` — and `-2` is exactly the suffix `new_run_id` appends on a local id collision, so this could strand or kill a live sibling run's session inside a *single* repository. `sessions_for_run` now matches the full session-name shape; the bare `pm-` prefix sweep survives only for `stop --scavenge` with no run id. Found while investigating why the test suite could not be run in parallel; the parallel failures were the symptom, the collision was the defect.
- **A failed launch no longer strands a running Developer session.** `start_slice` creates the tmux session, then waits for readiness and injects the prompt, and only afterwards records the session name in `current_slice`. Both intervening steps fail closed by design — on a trust prompt, a visible credential/approval prompt, or a session that exits early — and any of them left a live harness session that no state named, so `observe`, `finalize`, and `stop`'s recorded-session path were all blind to it while it kept running. The session is now force-stopped before the error propagates.

- **The repository's own `ruff` findings are at zero.** The `lint` skill reports only what a change *introduces*, so ten pre-existing findings had accumulated invisibly across the tree. Cleared: six unused imports and one unused local (dead code the skill's own rules call defects), `zip()` without `strict=` in `pm init`'s slice table — where a silent length mismatch would print fewer slices than the frozen plan contains, to the operator reading that output to confirm it — a `raise` inside `except` losing its traceback, and a naive `datetime.now()` naming orchestrator run directories. That last one is `datetime.now().astimezone()` rather than a UTC conversion on purpose: run directories are named in local wall-clock time, and switching them to UTC would have silently shifted new names by the operator's offset and broken sorting against every directory already on disk.
- **A PM steer no longer arrives as several truncated messages — no tmux injection carries more than one line.** `finalize --steer` pasted the whole correction into the live pane via `tmux load-buffer`/`paste-buffer`, and an operator observed opencode splitting one long correction into multiple separately-submitted messages at roughly 2,000 characters. The cause is upstream and unfixable from here: opencode's TUI (`opentui`) parses stdin chunk by chunk and loses bracketed-paste state when a paste spans more than one OS `read()`, so the embedded newlines are taken as Enter presses (opencode/opentui #3927, #758, #3397). No flag disables it, and the split point is a function of the tmux→pty→Bun chunk size rather than a documented constant. The correction is now written verbatim to `steer-attempt-<n>.md` in the slice artifact directory and only a one-line pointer is injected — exactly the split `start-slice` already used for `prompt.md` against the *other* TUI failure mode (silent truncation of a multi-KB paste at a fixed input-buffer size, PM Test 20 Finding 1). A single line has no newline to misread and a chunk boundary inside it merely appends to the input buffer, so splitting is structurally out of reach; truncation is defeated in practice by a pointer two orders of magnitude below the observed limit, not by a bound in the code. `send_correction` was deleted rather than repaired: once it refused newlines it was byte-identical to the existing `send_line`, whose one behaviour it needed. The invariant now holds module-wide and is recorded there — `send_prompt` and `send_line` both refuse a newline, so multi-line content can only ever reach a session as a file the pointer names. One further consequence: a steer is now durably readable in the artifact tree, where before it existed only in the run event log. Two delivery defects on the shared `send_line` path were fixed alongside it, both surfaced by review: its first `C-m` return code was ignored, so a pane exiting between typing and submission recorded a delivered steer that never arrived and spent an attempt; and its second `C-m` was unconditional, so an Enter could blindly answer a credential, approval, or trust prompt that the first Enter had just surfaced — `send_prompt` already rescanned for exactly that, and `send_line` now does too. The correction file is created exclusively, so a retry reusing an attempt number a failed `save_state` never persisted stops for a human instead of silently rewriting words the Developer may already have been pointed at. Net three tests fewer: six deleted covered a paste path that no longer exists, three added cover the collision, the withheld second Enter, and the marker classification.
- **Codex delegate continuations launch, and the codex sandbox is now an actual boundary.** `codex exec resume` accepts a smaller flag set than `codex exec` and rejects `--sandbox` and `-C` outright, so every orchestrator continuation on the codex harness failed at launch with `unexpected argument '--sandbox' found`. Both codex launch paths now express the sandbox as `-c sandbox_mode="<mode>"`, which the resume subcommand accepts and which was verified to override a resumed session's recorded sandbox in both directions — a `read-only` continuation of a `read-write` parent is genuinely read-only. `-C` is dropped on the resume path only, where it is rejected and redundant because the launcher already starts every delegate in the policy repository. The four other harnesses put resume on the same command as launch, so their flag sets cannot diverge this way; all four were checked and none compose a resume-rejected flag. A new regression test asserts the composed codex resume command against the set of flags the resume subcommand accepts, rather than against a denylist of known-bad ones.
- **Codex delegates and PM codex reviewers can no longer escalate out of their sandbox.** Both now pin `-c approval_policy="never"` instead of inheriting the caller's policy. Under an `on-request` policy — common in a personal `~/.codex/config.toml` — a sandbox-blocked command can be escalated by the model and granted by an automated approvals reviewer with no human present: verified against codex-cli 0.145.0, a `read-only` delegate escalated and wrote a file outside the repository, while the same command under `never` was refused. The advertised "mechanical read-only sandbox" was therefore unenforced in that configuration, on the fresh path as well as on resume; `references/codex.md` and the harness-profile table now attribute the guarantee to the pinned approval policy that actually provides it. Pinning `never` also removes an approval prompt no unattended delegate could answer.
- **A hard-stop marker no longer fires from inside an unrelated word.** `scan_hard_stop` matched every literal marker as a bare case-insensitive substring, so the bare token `MFA` matched any pane text containing `mfa` — including a random `tempfile` directory name, which the pane displays because the harness path and env prefix are echoed there. Found as a one-in-many test failure (`test_session_death_mid_wait_ends_wait_early` breaking early on `hard-stop scan: credential_prompt` from a harness that only sleeps and dies, with an empty pane tail), but it is a production defect in both operating directions: a false hard stop refuses every `send` and `finalize --steer`, fails floor fact 8 so no slice can be accepted, and ends `observe --wait` early. A marker that is a single bare word now matches on word boundaries; every other marker deliberately keeps substring matching, so a real prompt a pane renders flush against padding still matches. Getting that line right took two corrections, both caught by review or by an existing test: bounding *every* marker broke the mid-token pane-wrap case (`xxxEnter API key`), trading a false positive for the strictly worse false negative the `-J` fix below exists to prevent; and defining "single token" as "contains no whitespace" misclassified the hyphenated `two-factor`, which would then have missed `xxxTwo-factor`. The rule is now a pure word token. The accepted cost of substring matching for phrases is that negated or quoted prose can match (`no approval required`, `disallow access`) — that fails toward stopping, which is the safe direction for a floor fact.
- **Hard-stop detection no longer depends on pane width.** Pane capture now passes tmux `-J`, rejoining lines wrapped at the pane edge. A marker split mid-token ("Enter A" / "PI key to continue") survived `scan_hard_stop`'s whitespace normalization as "Enter A PI key" and matched nothing, so a visible credential, billing, or trust prompt could escape floor fact 8, the `send`/`steer` refusals, and `observe` purely because of where the line happened to wrap.

## [0.5.0] — 2026-07-13

### Added

- Mode B residual-finding propagation: every passing orchestrator result carries a structured `residual_findings` ledger, MC writes a per-slice `slice-summary.md`, and every run-state update refreshes an aggregate `run-report.md` so non-blocking post-plan considerations survive fresh sessions and repair rounds.

### Changed

- **Breaking:** Master Controller durable state and orchestrator results now use schema version 2. MC supports only the current complete state shape; runs missing the frozen plan digest, supervision/event state, repair state, worker posture, or recorded Git boundary must be reinitialized instead of being inferred or migrated.
