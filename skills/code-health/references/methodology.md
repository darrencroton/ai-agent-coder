# Measurement Methodology

## Evidence layers

- **Mechanical facts:** file inventory, line classifications, exact normalized repeated windows, Python AST nodes/imports, graph relationships, and Git counts.
- **Heuristic candidates:** a bounded reading list ordered from those facts. Candidate selection is not a verdict.
- **Agent judgment:** whether a measured structure is justified, risky, or worth changing. This never appears in the deterministic JSON bundle.

## Composition

The inventory comes from Git: tracked files plus untracked files not excluded by the repository's ignore rules. Duplicate index-stage rows are collapsed, and unresolved paths are recorded as a coverage limit. Symbolic links are listed as a coverage limit and never followed. Language is inferred from a recorded extension table. Test classification uses recorded path/name rules. Documentation and configuration remain separate from production and test source. V1 has no additional exclude or classification configuration; repository ignore rules are the only exclusion input.

Physical lines are partitioned into blank, comment, and code using the analyzer's recorded conservative lexical method. It recognizes comment-only lines rather than attempting full parsing, so inline and language-specific edge cases remain code. Treat cross-language comment ratios as approximate context, not a comparison target.

A language missing from the extension table produces **no coverage row at all**, so it would read as covered rather than unavailable. Two things close that hole: recognized languages include Fortran, Make, CMake, Meson and autotools even though none has a complexity or dependency collector, and every remaining unrecognized path is disclosed in `repository.unrecognised_extensions` — present in `detect` as well as `analyze`, but deliberately **not** counted by `--require-coverage`: whether an unclassified file is source is a judgement, and gating on it failed ordinary repositories over a `.babelrc`. Disclosure satisfies the invariant; the gate stays on measurement that actually failed for a language in scope.

That field is a map from unrecognized suffix (or bare filename, where there is no suffix) to file count, and it describes the **current** tree only. It is one field rather than a field plus a duplicate coverage limit, and grouped rather than listed, because on real repositories the listed form was dozens of scientific data tables per repository and buried the one entry that would have mattered. A base-only unrecognized path is not evidence about the tree as it stands now, so it does not appear. Data and build products (images, archives, binaries, tabular and scientific data) classify as `data` rather than unmeasured source, so that list stays a signal instead of an inventory dump. Configuration is matched by extension or by named dotfile rather than by a leading dot, because a dotfile holding shell code is unmeasured source and calling it configuration would hide exactly the gap this field exists to expose. Build files without an extension are matched by filename.

Comment detection is per language and deliberately conservative. Fortran covers free-form `!` only, so fixed-form `C` or `*` in column one counts as code (an undercount), while OpenMP and OpenACC directives such as `!$omp` count as comments even though they are semantically executable (an overcount in HPC sources). Make counts `#` only in column one, since a tab-indented `#` is a recipe line the shell interprets.

File distributions report raw count, minimum, median, upper quantiles, and maximum. A tail value means "inspect this file's role," not "split this file."

## Duplication

The built-in detector compares fixed-length windows of nonblank lines after removing whitespace. It does not strip comments, rename identifiers, or claim semantic clone detection. The evidence bundle records the minimum window and normalization rule.

Overlapping windows are reported once. A repeated 30-line block contains 25 overlapping 6-line windows, and reporting each one made three quarters of the evidence bundle redundant and filled the reading list with shifted views of the same site. A window is treated as continuing the previous one only when its **whole** occurrence set directly follows one shared predecessor with the same occurrence count, so a tail that repeats more often than its head keeps its own row instead of losing an occurrence to a longer block. Each row's `line_count` is measured from that row's own occurrences, so the cited lines and the claimed extent always describe the same block, and `minimum_window_lines` records the scan width. The fixed-width signature remains the comparison identity, so per-signature counts are unaffected by the merge; the *set* of rows carrying them is not, since a row is emitted only where a signature starts a run on one side or the other. A run extended at both ends therefore yields two rows citing the same site one window apart, both of them true. Because merging made extent a real measured value, each row also carries `base_line_count`, and a block that lengthened without repeating more times is a changed raw value in its own right. Two limits are accepted rather than engineered around: a run of identical consecutive lines is not collapsed, because deciding continuation by occurrence set cannot distinguish a window from its own successor; and a tail that repeats more often than its head keeps its own row, which ends the head's run early. Both under-report the extent, and because the reading list now ranks on extent, that under-report decides what a reader sees rather than merely how it is labelled. A 30-line block whose run is broken by one internal window that repeats elsewhere is emitted as two shorter rows, and five longer clean blocks can then fill the family and displace the largest duplication site in the tree. This is the one omission a reader cannot recover from the facts, because the truncated extent is what the facts record too; the two rows are only identifiable as one block by noticing that their occurrences are adjacent in the same files.

In a differential the same truncation can also invert. If the shape that truncated a run exists on only one side, the same block reports a longer extent on the other, so `line_count` can rise while duplication was in fact removed. The artefact is unbounded — a base run truncated at the scan width against a current run of forty windows reports an extent of forty-five against six — and it inflates the field the list ranks on, so such a row can take the top slot even though its `count_delta` is zero. Read `current_count` and `base_count` before treating an extent rise as growth. Correcting either exactly would need the cross-side merge state these limits exist to avoid.

Differential signatures compare both occurrence count and block extent: a clone that lengthens without repeating more often has a changed raw value, and `base_line_count` is what makes it comparable. When a changed block duplicates an untouched block, report the relationship and attribute investigation to the changed side. Do not blame the untouched file for the new relationship. Candidate selection implements the raw-value half of that rule only: a clone whose occurrence count and extent are both unchanged is not a candidate even when it moved into a changed file, so a copy deleted in one place and added in another passes silently. Its row, with `changed_side_occurrences` intact, is still in the facts. A block the change resolved keeps its row so the delta stays honest; having no current block, its occurrence lists are empty and `current_count` says why.

## Function complexity tiers

Python cyclomatic complexity is McCabe-style decision counting over stdlib AST functions. When installed, Lizard adds per-function cyclomatic evidence for its supported non-Python languages. One accepted limit: a Lizard run over the base revision that fails is not recorded, so its functions are absent rather than reported as an unavailable baseline, and a changed function can then look like a rise from zero. Filenames are passed after `--` so a path cannot be read as an option, which removes the reachable trigger; the residual case is disclosed here rather than given a coverage mechanism of its own. Every function record names its engine; distributions remain within a language and engine coverage tier. It is not cognitive complexity and scores from different algorithms are not interchangeable.

## Dependency graphs

Two collectors emit dependency evidence, and both describe the same units: one `nodes` row per file carrying `fan_in`, `fan_out` and reverse-reachability blast radius, plus `edges` and strongly connected components. A zero is not proof that a file is unused, and the two graphs are never merged into one number.

Reverse reachability counts the distinct other files that transitively reach a node. It is computed over the strongly-connected-component condensation, which is a DAG that Tarjan already emits in reverse topological order, so one backwards pass answers every node; ancestors accumulate in a per-component bitmask over files rather than a set of paths, because a set costs O(V^2) objects on a wide graph. It is not a restatement of `fan_in`: a header included by one file that a hundred files include has a fan-in of one and a blast radius of a hundred.

**Python** contains statically resolved internal imports. Dynamic imports, runtime plugin registration, optional imports, path manipulation, and reflection may be absent.

**C family** (every C, C++ and CUDA extension in the analyzer's table — read the coverage matrix rather than a list copied here) contains internal `#include "..."` edges found by a lexical scan. It is deliberately not a preprocessor:

- Only quoted includes are edges. `#include <...>` names a system or external header by contract and is excluded, so no header search path is required.
- Comments and raw string literals are blanked before scanning, so a commented-out include is not an edge. Ordinary string and character literals are skipped rather than blanked — an include's own target is a string, and blanking would erase what is being measured — so a literal such as `"/*"` or `"dir//b.h"` cannot be mistaken for a comment. Raw strings are disabled for `.c` translation units (C has none) and enabled elsewhere, including the C/C++-ambiguous `.h`. An identifier ending in `R` before `"(` is string concatenation rather than a raw-string opener, and an unterminated opener is not treated as a raw string at all, so a lexing mistake can never silently blank the rest of a file. A leading byte-order mark does not hide the first include.
- The masker is lexical, not a compiler. On input that does not compile — an unterminated block comment, a stray apostrophe, a line-splice inside a literal — masking can be wrong in either direction. An unterminated quote is bounded to its line so it cannot swallow the includes below it.
- An include inside `#if`/`#ifdef` still counts. The graph records what the source text says, not what a given build configuration compiles.
- A path is resolved against the including file's own directory, then repository-relative, then a unique basename. Separators are canonicalized before normalization, so a Windows-style path resolves the same way on either host.
- Escape is judged *after* resolving against the including directory, so `../include/b.h` from `src/` is ordinary and stays inside. Only a target that is absolute, drive-lettered, or still outside the root once resolved is recorded `outside_repository`, and it never reaches the basename fallback: an explicit path out of the tree is external coupling, not an invitation to guess a same-named file inside it.
- An exact target that exists in the repository but is not a measured C-family file — unreadable, a symlink, or another language — is named as such rather than resolved to a same-named file elsewhere. The basename fallback is a last resort, never a way to override a path that was written explicitly.
- Basename uniqueness is decided across the whole repository, not just measured files: an unmeasured same-named file makes the basename ambiguous rather than invisible to the guess. Every unresolved include is recorded with a line number and a reason: `ambiguous_basename` (more than one candidate anywhere in the repository), `in_repository_unmeasured_language` (the exact target exists but is not measured — unreadable, a symlink, or another language), `unique_unmeasured_basename` (no exact target; the one basename match is unmeasured), `outside_repository`, `not_in_repository`, or `self_include`.
- Both sides of a differential use the same inventory and therefore the same resolution rules, so a base-side guess cannot manufacture a base relationship that hides a real new one.
- Macro-computed includes and continuation lines are invisible. A unique basename can still resolve to the wrong file — a vendored copy, a build artifact, or a target that really comes from an `-I` path outside the repository. Every edge therefore records how it was resolved in `via` (`exact_relative`, `repository_relative`, `unique_basename`), and `resolution_counts` totals those provenances. **Read that ratio before trusting the graph.** A project whose headers are found through `-I` search paths rather than relative includes resolves most of its edges by basename: on one real repository 651 of 794 edges were basename guesses, which makes the graph a plausible reconstruction rather than a proven one. The guessed edges were previously also listed individually, which at that scale restated the whole edge list and buried the ratio that matters.

One graph spans the whole C family, so a single unreadable member makes the dependency row `unavailable` for every C-family language rather than only its own.

An include cycle is normal in C where header guards make it harmless; it is a prompt to check that the guards exist and that the coupling is intended, never a defect on its own.

## Differential semantics

Compare the current tracked-plus-untracked tree with the explicit Git base. A regression bucket requires a changed raw value or a new relationship. A dependency cycle counts as new unless its members were already mutually connected in a single base cycle *and* every edge between them already existed. Shrinking a cycle therefore reports nothing, while rewiring one into a smaller cycle with a new edge reports it, and a cycle absent from every base cycle is new even if no member file changed.

A file the base could not supply makes the baseline incomplete, whether it was unreadable or failed to parse: the affected coverage rows are `unavailable` rather than clean, the paths are listed in `facts.base_unreadable_files` or the `base_parse_errors` coverage limit so the cause is traceable, and any delta or cycle candidate that only its absence would produce is suppressed rather than reported as a change.

What each failure invalidates is stated precisely, from one derivation shared by the coverage matrix, the disclosed limits and candidate suppression. An **unreadable** base file voids every metric family for its language, and — because one include graph spans the whole C family — voids the dependency row for every C-family language in scope. A base **parse** failure voids only the families that need an AST: the text itself read fine, so composition and duplication stay covered, and a file-size delta against that base is still reported. Duplication is different again, because one signature space spans every language at once: a base file that could not be read at all understates a base count anywhere, so it voids `duplication` for every language in scope and suppresses differential duplication candidates. That fires only when the file is also in the change, compared under base-path identity so a rename is matched by the name the base knew it by. The comparison is deliberately coarse in one direction: a file that is renamed but stays unreadable, or is renamed into a classification that contributes no windows, is missing from both pools yet still voids duplication. Recognising that would mean carrying current-pool membership through the baseline, which costs more than the conservative reading it would avoid; it fails closed, never producing a phantom rise or a false clean. The current side carries no matching rule, so an undecodable file in the working tree still leaves other languages' duplication reading `covered` while the pool is short of its text; that is a pre-existing limit of the absolute measure, disclosed here rather than turned into a repository-wide coverage failure. A base-only failure in a language the current tree no longer contains produces no coverage row and demands no coverage, because there is nothing left to compare. When a reported cycle's members were already mutually connected at the base, the row carries `new_edges` and says so, rather than implying the whole cycle is new. Rank movement caused by population changes is context only. Renames should map base identities to current paths before signatures are compared.

## Git churn context

`--history` is optional because it depends on clone completeness and the chosen window. History is refused outright on a shallow clone rather than computed from a truncated log. It is one `git log --max-count=N --format=%H --numstat --no-renames`: rename detection is off so churn keys stay literal repository paths, and a pre-rename and post-rename name remain separate facts that join against the rest of the bundle. Binary files report `-` rather than a line count, so their revisions are retained and their line deltas omitted. Only revision and line counts are recorded; author identities are not. Churn prioritizes inspection and never enters a changed, worsened or resolved structural bucket.

## Interpreting disproportionality

To assess whether complexity seems disproportionate to role:

1. Identify the component's role from callers, public interfaces, tests, and documentation.
2. Compare its raw structure with peers that have the same role and measurement coverage.
3. Check whether complexity is inherent, concentrated at a boundary, generated, or compensating for external constraints.
4. State the plausible maintenance consequence before recommending change.
5. Prefer `no change justified` when evidence does not support intervention.
